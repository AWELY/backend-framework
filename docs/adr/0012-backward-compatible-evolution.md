# 0012. Backward-compatible evolution of the API

- Status: Accepted
- Since: 1.0.0

## Context

Three consumers ship with the repository and act as the acceptance test for every change: the Maa
Store storefront (`storefront/`), the demo store (`examples/demo-store/`) and stores generated by the
CLI. Third-party plugins build on the exported API. The hardening touched every layer, and the rule
in `docs/ROADMAP.md` was that existing clients keep working unless a break is unavoidable and
written down.

## Decision

Change is additive or opt-in by default:

- **Responses only grow.** New fields may appear; existing fields are not removed, renamed or
  retyped.
- **Arrays stay arrays.** List endpoints keep returning a bare JSON array. The total goes in the
  `X-Total-Count` header (exposed through CORS), not in a new envelope.
- **The error body is additive.** `{ "error": { "message", "details" } }` gained `code` and
  `requestId`. Clients should branch on `code`; message texts that clients already depend on are kept
  (the storefront matches "Invalid or expired token" to drop a dead session).
- **New behaviour is opt-in.** `Idempotency-Key` and `If-Match` are optional headers; `basePath`
  defaults to none; checkout and cart-creation limits default to off; `/metrics` works without a
  token unless one is configured.
- **Legacy helpers stay.** `validateBody` (prefer `withInput`), `requireApiKey`, `optionalApiKey`,
  `requireRole` (prefer `createAuthenticator` and `requirePermission`), `ExtensionRegistry.emit`
  (prefer the outbox), `ModuleContext.loginLimiter` and `registrationLimiter` (prefer `limiters`).
- **Validation stays lenient where clients relied on it.** `null` on a non-nullable field still
  means "not sent"; unknown query keys are ignored.
- **The schema evolves forward only.** Migrations are append-only and never edited once released.
  Constraints that legacy rows might violate are added `NOT VALID`, then validated with a warning
  instead of a failed migration (0920).
- **Every unavoidable break is listed** under "Breaking changes" in `CHANGELOG.md` with what to do.
- **Guard rails.** `docs/openapi.json` is regenerated and compared in CI; the semver rules are in
  `docs/VERSIONING.md`.

## Consequences

- The storefront, the demo store and generated stores ran unchanged through Phase 2 (its exit test).
- Some shapes are less tidy than a fresh design: pagination metadata lives in a header, and there are
  two ways to validate a body and to check the owner key.
- Legacy surface must be maintained and tested until a major release removes it.
- The 1.0.0 breaks that could not be avoided (sessions, payment state machine, events after commit)
  are concentrated in one release with migration notes.

## Alternatives considered

- **A `{ data, meta }` envelope for every response.** Cleaner, and breaks every client at once.
- **Serve new shapes under `/v2`.** `basePath` makes this possible later; running two contracts over
  one database is not worth it for additive changes.
- **Break freely because 0.x promised nothing.** Rejected: the three bundled consumers are the
  evidence that the framework is usable, and breaking them would remove that evidence.
