# متجر AMA: إلكترونيات وإكسسوارات الهواتف

متجر إلكتروني تجريبي كامل في **طرابلس - تاجوراء**، مبني فوق الإطار. هو التطبيق العملي الذي ينص عليه المقترح: ربط الإطار بموقع حقيقي، بثلاث واجهات لثلاثة مستخدمين:

| المستخدم | الواجهة | الرابط |
|---|---|---|
| **الزبون** | المتجر: تصفح، وسلة، وإتمام الطلب، وتتبّع، وحساب فيه طلباته وبياناته | http://localhost:5173 |
| **مدير المتجر** | لوحة التحكم: الطلبات، وتعيين المندوبين، والمنتجات، والمخزون، والأقسام، والزبائن، والموظفون، والتقارير | http://localhost:5173/admin/ |
| **مندوب التوصيل** | تطبيق للهاتف: طلباته، والاتصال بالزبون، و"استلمت من المحل"، و"تم التسليم" | http://localhost:5173/courier/ |

```
storefront/
├─ api/                 خادم المتجر: يستخدم الإطار كمكتبة
│  ├─ app.js            إعدادات المتجر: المدن وأسعار التوصيل، والإضافات، وجدول الأدوار (ROLES)
│  ├─ plugins/          إضافات خاصة بهذا المتجر (انظر "ما بُني فوق الإطار" أدناه)
│  │  ├─ staff.js       حسابات الموظفين (مدير ومندوب) والدخول
│  │  ├─ delivery.js    تعيين المندوبين، والاستلام، والتسليم، وتحصيل النقد
│  │  ├─ customer-orders.js  سجل مراحل الطلب، وإلغاء الزبون لطلبه
│  │  ├─ reports.js     أرقام لوحة التحكم (المبيعات، والأكثر مبيعاً، والمخزون)
│  │  └─ shared.js      أدوات مشتركة بين الإضافات
│  ├─ seed.js           الكتالوج التجريبي وحسابات الموظفين التجريبية
│  └─ create-staff.js   إنشاء حساب موظف من الطرفية
├─ web/                 الموقع: HTML + CSS + JavaScript بلا أي مكتبة
│  ├─ index.html …      صفحات المتجر (الرئيسية، والمنتج، والسلة، والطلب، والحساب، وطلباتي، والتتبّع)
│  ├─ admin/            صفحات لوحة التحكم (سكربتاتها في js/admin)
│  ├─ courier/          تطبيق المندوب (سكربته في js/courier/app.js)
│  ├─ css/styles.css    تصميم المتجر (ويستخدمه الكل للألوان والأزرار والحقول)
│  ├─ css/admin.css     تصميم لوحة التحكم وتطبيق المندوب
│  └─ js/               api.js (الاتصال بالـ API)، و ui.js (الأدوات المشتركة)، و pages/ و admin/ و courier/
├─ web-server.js        خادم صغير يعرض الموقع (بلا مكتبات)
├─ start.js             يشغّل الخادمين معاً
└─ tests/browser.mjs    اختبار في متصفح حقيقي (الزبون، ثم المدير، ثم المندوب)
```

**Headless:** الموقع والـ API **خادمان منفصلان**. يحمّل المتصفح الصفحات من الأول (المنفذ 5173)، ويتصل بالثاني (المنفذ 3000) مباشرة. لوحة التحكم وتطبيق المندوب "عميلان" آخران لنفس الـ API، تماماً مثل المتجر: لا شيء منها يتصل بقاعدة البيانات مباشرة.

## التشغيل

المتطلبات: أن يكون الإطار مبنياً (`npm install` ثم `npm run build` في المجلد الرئيسي)، وPostgreSQL تعمل.

**1. قاعدة بيانات المتجر** (مرة واحدة)

على ويندوز:
```powershell
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -h localhost -U postgres -d postgres -c "CREATE DATABASE ama_store OWNER commerce_app;"
```

على Linux:
```bash
cd /tmp && sudo -u postgres psql -c "CREATE DATABASE ama_store OWNER commerce_app;"
sudo -u postgres psql -d ama_store -c "ALTER SCHEMA public OWNER TO commerce_app;"
```

**2. الإعداد** (مرة واحدة، داخل مجلد `storefront`)

```bash
cd storefront
npm install
npm run setup -- --db-password كلمة_مرور_commerce_app
npm run migrate
npm run seed
```

`migrate` ينشئ جداول الإطار، ثم جداول إضافات المتجر (`staff` و `deliveries` و `order_events`). و`seed` يضيف الكتالوج والحسابات التجريبية.

**3. التشغيل**

```bash
npm start
```

ثم افتح **http://localhost:5173** في المتصفح. للإيقاف: `Ctrl + C`.

> **بعد تعديل الإطار نفسه:** `npm run build` في المجلد الرئيسي، ثم `npm install` هنا من جديد (المتجر يثبّت نسخة من الإطار، انظر `.npmrc`).

## الحسابات التجريبية

ينشئها `npm run seed` لتجربة اللوحة والتطبيق فوراً. **كلمات مرورها معروفة، فهي لقاعدة تجريبية فقط**، ولا تُنشأ أبداً إن كان `NODE_ENV=production` (عندها يملأ `seed` الكتالوج وحده).

| الدور | البريد | كلمة المرور | يدخل من |
|---|---|---|---|
| مدير المتجر | `admin@ama.ly` | `Ama@admin2026` | `/admin/` |
| مندوب: أحمد سالم | `ahmed@ama.ly` | `Ama@courier2026` | `/courier/` |
| مندوب: خالد عمر | `khaled@ama.ly` | `Ama@courier2026` | `/courier/` |

صفحة دخول اللوحة تقبل الدورين: المدير يذهب إلى لوحة التحكم، والمندوب إلى تطبيقه. وفي أسفل كل صفحة من المتجر رابطان: "لوحة المتجر" و"تطبيق المندوب".

**على متجر حقيقي:** أنشئ أول مدير من الطرفية، ثم أوقف الحسابات التجريبية من صفحة "الموظفون والمندوبون" في اللوحة:

```bash
npm run create-staff -- --role admin --name "علي" --email ali@example.ly --password "كلمة-مرور-قوية"
```

بعدها يضيف المدير باقي الموظفين والمندوبين من اللوحة نفسها.

## رحلة الطلب كاملة (جرّبها بنفسك)

1. **الزبون** يطلب من المتجر (كضيف أو بحسابه)، ويختار مدينته والدفع عند الاستلام.
2. **المدير** يرى الطلب "جديداً" في اللوحة (والعدد بجانب "الطلبات")، يتصل بالزبون ثم يضغط **تأكيد الطلب**.
3. **المدير** يختار مندوباً من قسم "التوصيل" ويضغط **تعيين**.
4. **المندوب** يرى الطلب في تطبيقه (يتحدث وحده كل دقيقة)، يأخذه من المحل ويضغط **استلمت الطلب من المحل**، فيصبح الطلب "في الطريق".
5. **المندوب** يسلّمه ويضغط **تم التسليم واستلمت المبلغ**: الطلب "تم التسليم"، والدفع "مدفوع" باسم المندوب.
   إن واجه مشكلة (الزبون لا يرد مثلاً) يضغط **إبلاغ عن مشكلة**، فتظهر الملاحظة للمدير في جدول الطلبات.
6. **الزبون** يرى كل مرحلة ووقتها في "طلباتي" أو "تتبّع طلبك". وما دام الطلب "قيد المراجعة" يستطيع إلغاءه بنفسه.

طلب "الاستلام من المحل" لا يحتاج مندوباً: المدير يؤكده، ثم **جاهز للاستلام**، ثم **استلمه الزبون**.

## ما بُني فوق الإطار (دون تعديل سطر فيه)

كل ما تحتاجه اللوحة وتطبيق المندوب بُني في `api/plugins/` كإضافات للمتجر، بالواجهة العامة للإطار فقط (`require("commerce-framework")`). هذا هو الاختبار الحقيقي لقابلية الإطار للتوسعة:

| الحاجة | كيف حُلّت | نقطة التوسع في الإطار |
|---|---|---|
| أدوار جديدة: مدير ومندوب | `ROLES` في `app.js` | `accessControl` (يفحص الصلاحية لا اسم الدور) |
| دخول الموظفين | `plugins/staff.js` يصدر توكناً بنفس سر الإطار | `signToken` و `hashPassword` و `FailureLimiter` |
| جداول جديدة | migrations بأرقام 9000+ | `migrations` في الإضافة |
| تعيين مندوب وتغيير حالة الطلب | `plugins/delivery.js` | `ORDERS_SERVICE` من حاوية الـ DI (آلة الحالات تبقى سارية) |
| سجل مراحل الطلب | `plugins/customer-orders.js` يستمع للأحداث | `extensions.on("order.statusChanged")` وأخواتها |
| أرقام اللوحة | `plugins/reports.js` | `router` و `pool` |

**ما كشفه بناء موقع حقيقي في الإطار** (فرص تحسين له، موثقة في تعليقات الكود):
- **لا مسار لمخزون عدة منتجات دفعة واحدة:** `GET /inventory/:id` منتج واحد، فالصفحة الرئيسية ترسل طلباً لكل منتج. اللوحة تستخدم `/admin/stock` من إضافة التقارير بدلاً منه.
- **`changeStatus` لا تقبل شرط "الحالة المتوقعة":** بين فحص "قيد المراجعة" وإلغاء الزبون لحظة قد يؤكد فيها المدير الطلب (نافذة صغيرة جداً، موثقة في `customer-orders.js`).
- **`changeStatus` تفتح معاملتها الخاصة:** فلا يمكن جمع "تسجيل الاستلام" وتغيير الحالة في معاملة واحدة (الإضافة تتراجع يدوياً عند الفشل، انظر `delivery.js`).
- **الزبون المسجل لا يستطيع تتبّع طلب ضيف برقم الهاتف:** قاعدة `GET /orders/:id` تعطي الزبون طلباته هو فقط ولا تجرّب الهاتف معه.
- **لا بحث نصي في الطلبات:** البحث في صفحة الطلبات باللوحة يعمل على الصفحة المعروضة فقط.

## التخصيص

| ماذا | أين |
|---|---|
| المدن وأسعار التوصيل، والتوصيل المجاني فوق 500 د.ل | `api/app.js` (`DELIVERY_RATES`) |
| رسالة الدفع عند الاستلام، والاستلام من المحل | `api/app.js` |
| صلاحيات المدير والمندوب | `api/app.js` (`ROLES`) |
| اسم المتجر، العنوان، **رقم واتساب** (يظهر زر عائم عند وضعه) | `web/js/config.js` |
| الألوان والخطوط | `web/css/styles.css` (المتغيرات في أوله) |
| صور المنتجات | في `web/images/products/`: صورة لكل منتج باسم الـ slug (`<slug>.webp`، 800×800). أو من اللوحة: صفحة المنتج، حقل "رابط الصورة". مصادر الصور في `CREDITS.md` هناك |
| الأيقونات | `web/js/icons.js`: أيقونات SVG بدل الإيموجي، لتظهر بنفس الشكل على كل الأجهزة |

**التصميم:** ألوان الشعار (كحلي وبرتقالي)، وخطّان: Readex Pro للعناوين والأسعار، و IBM Plex Sans Arabic للنصوص. العنصر المميز الوحيد هو **ملصق السعر** البرتقالي (`.tag`)، وكل ما حوله هادئ.

## الأمان في الموقع

- **منع حقن الكود:** كل نص يأتي من الـ API يُهرَّب قبل عرضه (`esc` في `js/ui.js`)، في المتجر واللوحة والتطبيق.
- **سياسة أمان المحتوى (CSP):** المتصفح لا يشغّل إلا سكربتات الموقع نفسه، ولا يتصل إلا بـ API المتجر.
- **الوصول للملفات:** خادم الموقع لا يسمح بالوصول لأي ملف خارج مجلد `web` (مثل `.env`).
- **CORS:** الـ API يقبل الطلبات من عنوان الموقع فقط (`CORS_ORIGIN`).
- **جلستان منفصلتان:** توكن الزبون وتوكن الموظف في مفتاحين مختلفين في المتصفح، فلا يُرسل توكن المدير أبداً من صفحات المتجر.
- **حماية اللوحة في الخادم لا في الصفحة:** فحص الدخول في صفحات اللوحة للراحة فقط؛ كل مسار في الخادم يفحص الصلاحية بنفسه.
- **الحساب الموقوف:** مسارات الإضافات تفحص في القاعدة مع كل طلب أن الموظف ما زال نشطاً، فالمندوب الموقوف لا يستطيع أي عملية توصيل فوراً. ومدة توكن الموظف 12 ساعة فقط (التوكن في الإطار بلا جلسة في الخادم، فلا يُلغى قبل انتهاء مدته في مسارات الإطار نفسها).
- **الدخول:** حد للمحاولات الفاشلة لحسابات الموظفين (8 كل 15 دقيقة)، ونفس الرسالة للبريد غير الموجود ولكلمة المرور الخاطئة.

## الاختبار

- **ضمن الفحص الشامل:** `npm run verify` في المجلد الرئيسي يفحص المتجر أيضاً: كل الصفحات (المتجر واللوحة والتطبيق) وسياسة الأمان، ومدن التوصيل، وCORS، ودخول الموظفين وفصل صلاحياتهم، وصياغة كل السكربتات.
- **اختبار في متصفح حقيقي:** شغّل المتجر (`npm start`) بعد `npm run seed`، ثم في نافذة أخرى:
  ```bash
  npm run test:browser
  ```
  - **ماذا يفعل:** يفتح Edge أو Chrome أو Chromium بلا واجهة (على ويندوز وLinux وmacOS)، ويمر بثلاث رحلات:
    1. **الزبون:** تصفح، وبحث، وسلة، وإتمام طلب، وتتبّع، وتسجيل، و"طلباتي".
    2. **المدير:** يدخل اللوحة، ويؤكد طلب الضيف، ويعيّن له مندوباً.
    3. **المندوب:** يدخل التطبيق على شاشة هاتف، ويستلم الطلب ويسلّمه، ثم يتأكد أن صفحة التتبع تقول "تم التوصيل" والدفع "مدفوع".
  - **ماذا يفحص:** أي خطأ JavaScript أو مخالفة لسياسة الأمان، وأي تمرير أفقي في أي صفحة.
  - **فحص الحقن (XSS):** ينشئ منتجاً مؤقتاً اسمه يحتوي كود HTML (بمفتاح `OWNER_API_KEY` من `.env`)، ويتأكد أنه يظهر كنص عادي في المتجر **وفي جدول المنتجات باللوحة**، ثم يحذفه.
  - **منافذ أخرى:** `SITE=http://localhost:5273 API=http://localhost:3100 npm run test:browser`.
  - **الصور:** يلتقط صورة لكل صفحة في `tests/screenshots/`.
  - **تنبيه:** ينشئ طلبات وحسابات حقيقية، فشغّله على قاعدة تجريبية فقط. لإعادة المتجر نظيفاً: امسح القاعدة ثم `npm run migrate` و`npm run seed`.
