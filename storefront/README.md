# متجر ماء (Maa Store) — إلكترونيات وإكسسوارات الهواتف

متجر إلكتروني تجريبي في **طرابلس - تاجوراء**، مبني فوق إطار **Maa** (الحزمة `maa`). هو التطبيق العملي الذي ينص عليه المقترح: ربط الإطار بمتجر حقيقي من البداية إلى النهاية، من تصفّح الزبون حتى تسليم المندوب.

## الواجهات الثلاث

كلها صفحات HTML + CSS + JavaScript بلا أي مكتبة، وتتصل بنفس الـ API:

| الواجهة | الرابط | من يدخل | ماذا يفعل |
|---|---|---|---|
| **موقع الزبون** | http://localhost:5173 | أي زائر (الحساب اختياري) | تصفح وبحث، وأشكال المنتج، وسلة، وكوبون، وإتمام الطلب بالدفع عند الاستلام أو بالبطاقة التجريبية، وتتبّع الطلب، وحسابي و"طلباتي" |
| **تطبيق المندوب** | http://localhost:5173/courier.html | حساب مندوب | الطلبات المسندة إليه، واستلامها من المحل، وتسليمها مع تسجيل النقود المحصّلة، أو تسجيل محاولة فاشلة. مصمم للهاتف أولاً |
| **لوحة الإدارة** | http://localhost:5173/admin.html | المدير والمشرف وخدمة العملاء، أو المالك بمفتاحه | الطلبات وإسنادها للمندوبين والاسترجاع، والتوصيلات، والمنتجات والأشكال والمخزون، والأقسام، والكوبونات، والزبائن، والموظفون، وسجل التدقيق |

│  ├─ admin.html           لوحة الإدارة
│  ├─ js/pages/            سكربت كل صفحة من صفحات الزبون
│  ├─ js/staff/            لوحة الإدارة (admin*.js) وتطبيق المندوب (courier.js) ودخول الموظفين (common.js)
│  ├─ js/config.js         اسم المتجر، والعنوان، ورقم واتساب
│  └─ css/                 styles.css (الموقع) و app.css (تطبيقا الموظفين)

**Headless:** الموقع والـ API **خادمان منفصلان**. يحمّل المتصفح الصفحات من الأول (المنفذ 5173)، ويتصل بالثاني (المنفذ 3000) مباشرة. هذا ما يعنيه "Headless" في عنوان المشروع: يمكن استبدال الموقع بتطبيق جوال دون تغيير سطر في الإطار، وتطبيق المندوب ولوحة الإدارة مثالان على ذلك: واجهتان أخريان فوق نفس الـ API.

## التشغيل

المتطلبات: أن يكون الإطار مبنياً (`npm install` ثم `npm run build` في المجلد الرئيسي)، وPostgreSQL تعمل، ومستخدم القاعدة `commerce_app` موجوداً (من `docs/SETUP.md` أو `docs/SETUP-LINUX.md`).

**1. قاعدة بيانات المتجر** (مرة واحدة)

على ويندوز:
```powershell
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -h localhost -U postgres -d postgres -c "CREATE DATABASE ama_store OWNER commerce_app;"
```

على Linux:
```bash
cd /tmp && sudo -u postgres psql -c "CREATE DATABASE ama_store OWNER commerce_app;"
sudo -u postgres psql -d ama_store -c "ALTER SCHEMA public OWNER TO commerce_app;"
```

اسم القاعدة `ama_store` والمستخدم `commerce_app` هما ما يكتبه `npm run setup` في `DATABASE_URL`. لاسم آخر، عدّل `DATABASE_URL` في `storefront/.env` بعد الخطوة التالية.

**2. الإعداد** (مرة واحدة، داخل مجلد `storefront`)

```bash
cd storefront
npm install
npm run setup -- --db-password كلمة_مرور_commerce_app
npm run migrate
npm run seed
```

| الأمر | ماذا يفعل |
|---|---|
| `npm run setup` | ينشئ `storefront/.env` من `.env.example` بأسرار عشوائية (`OWNER_API_KEY` و`AUTH_TOKEN_SECRET`). لا يكتب فوق `.env` موجود |
| `npm run migrate` | ينشئ الجداول أو يحدّثها (تشغيله مرة ثانية آمن) |
| `npm run seed` | 6 أقسام و16 منتجاً بصورها، وأشكال لبعضها، وكوبونان، وخمسة حسابات موظفين. يطبع الحسابات في النهاية. تشغيله مرتين آمن |

**3. التشغيل**

```bash
npm start
```

ثم افتح **http://localhost:5173** للموقع، و**/admin.html** للوحة الإدارة، و**/courier.html** لتطبيق المندوب. للإيقاف: `Ctrl + C` (يوقف الخادمين معاً). يمكن تشغيل كل خادم وحده: `npm run api` و`npm run web`.

**بعد تعديل الإطار:** المتجر يثبّت الإطار نسخة حقيقية في `node_modules` (`install-links=true` في `.npmrc`)، فبعد `npm run build` في المجلد الرئيسي نفّذ `npm install` هنا من جديد ليصل التعديل.

## حسابات التطوير

ينشئها `npm run seed` (القائمة في `api/seed.js`، `STAFF`). **للتطوير فقط**: في أي متجر حقيقي غيّر كلمات المرور من قسم "الموظفون" في لوحة الإدارة (بمفتاح المالك) أو احذف الحسابات.

| الدور | البريد | كلمة المرور | يدخل إلى |
|---|---|---|---|
| مدير (`admin`) | `admin@maa.ly` | `maa-admin-2026` | لوحة الإدارة (كل الأقسام ما عدا تعديل الموظفين). ويستطيع دخول تطبيق المندوب أيضاً |
| مشرف (`manager`) | `manager@maa.ly` | `maa-manager-2026` | لوحة الإدارة: الكتالوج والطلبات والإسناد، دون الاسترجاع |
| خدمة العملاء (`support`) | `support@maa.ly` | `maa-support-2026` | لوحة الإدارة: الطلبات وحالتها ودفعها، والزبائن |
| مندوب (`courier`) | `courier1@maa.ly` | `maa-courier-2026` | تطبيق المندوب |
| مندوب (`courier`) | `courier2@maa.ly` | `maa-courier-2026` | تطبيق المندوب |
| المالك | — | قيمة `OWNER_API_KEY` من `storefront/.env` | لوحة الإدارة بخيار "الدخول بمفتاح المالك": كل شيء، ومنه وحده إنشاء الموظفين وتعديلهم. المفتاح يُحفظ في `sessionStorage` فقط (يُنسى بإغلاق التبويب) |

صلاحيات كل دور هي `DEFAULT_ROLES` في الإطار (`src/engine/access-control.ts`، والجدول في `../docs/API.md`). الواجهة تخفي ما لا يملكه الدور، لكن القرار الحقيقي في الخادم دائماً (403).

**بيانات تجريبية أخرى:** الكوبونان `WELCOME10` (خصم 10%) و`SAVE20` (خصم 20 د.ل على طلب من 200 د.ل فأكثر). وأشكال: "جراب سيليكون" بثلاثة ألوان (الأزرق نفد عمداً)، و"ساعة ذكية رياضية" بمقاسين (46 ملم بسعر خاص).

## وضع التجربة (`DEMO_MODE`)

`DEMO_MODE=true` في `storefront/.env` (الافتراضي، إلا إن كان `NODE_ENV=production`). اجعله `false` في الإنتاج.

**الدفع بالبطاقة التجريبية** (إضافة `api/plugins/demo-card-gateway.js`): تعمل كبوابة حقيقية "مستضافة"، مبنية فقط على الواجهة العامة `require("maa")`:

1. في إتمام الطلب يختار المشتري "بطاقة مصرفية (تجريبي)". يُنشأ الطلب بحالة دفع `pending`، والبضاعة محجوزة 15 دقيقة (`paymentExpiresAt`)، ورد الطلب يحمل `payment.redirectUrl`.
2. الموقع ينقل المشتري إلى `pay.html?order=…&phone=…`، التي تقوم مقام صفحة البنك. يختار "ادفع" أو "محاكاة رفض البطاقة" (لا تُدخل بيانات بطاقة حقيقية).
3. الصفحة ترسل النتيجة إلى `POST /payments/card/simulate` (يقوم مقام خوادم البنك، ويتطلب رقم الطلب وهاتفه معاً).
4. "البنك" يستدعي `POST /payments/card/webhook` عبر HTTP حقيقي، بتوقيع HMAC على الجسم الخام في ترويسة `X-Demo-Signature`. الـ webhook يتحقق من التوقيع أولاً، ثم يسجّل الدفع (`paid` أو `failed`). الـ webhook المكرر لا يغيّر شيئاً.
5. إن لم يُدفع الطلب خلال 15 دقيقة، يلغيه الإطار تلقائياً ويعيد مخزونه. والاسترجاع من لوحة الإدارة يمر عبر `refund` في الإضافة.

سر التوقيع `DEMO_GATEWAY_SECRET` اختياري (يُشتق من `AUTH_TOKEN_SECRET` إن تُرك فارغاً). البوابة التجريبية مثبتة دائماً في `api/app.js`؛ في متجر حقيقي استبدلها ببوابة حقيقية (نموذج: `../examples/plugins/hosted-gateway.ts`).

**صندوق بريد التطوير** (إضافة `api/plugins/dev-mailbox.js`): الإطار لا يرسل بريداً بنفسه، بل يطلق أحداثاً. هذه الإضافة تستمع لها وتحفظ الرسائل في الذاكرة (آخر 200) وتكتبها في سجل الخادم، بدل إرسالها بالبريد أو SMS:

| الحدث | الرسالة |
|---|---|
| `customer.passwordResetRequested` | رابط `reset.html?token=…` لتعيين كلمة مرور جديدة |
| `order.created` | تأكيد الطلب ورابط تتبّعه (إلى هاتف الطلب) |
| `order.deliveryChanged` | "أُسند للمندوب"، "في الطريق"، "تم التوصيل"، "لم نستطع التوصيل" |

`GET /dev/mailbox?to=<بريد أو هاتف>` يعرض الرسائل، **فقط مع `DEMO_MODE=true`**. في صفحة "نسيت كلمة المرور" يظهر رابط الاستعادة مباشرة من الصندوق في وضع التجربة. في متجر حقيقي استبدل الإرسال ببريد أو SMS.

## ما يستخدمه كل جزء من الإطار

| الصفحة | ميزات الإطار |
|---|---|
| الرئيسية (`index.html`) | `GET /products?q=&sort=&categoryId=&limit=&offset=` (البحث والترتيب والترقيم في الخادم)، والعدد الكلي من `X-Total-Count`، و`GET /categories`، و`GET /inventory/:productId` |
| المنتج (`product.html`) | `GET /products/by-slug/:slug` أو `/products/:id` مع الأشكال، ومخزون كل شكل، والإضافة بـ `variantId` (`VARIANT_REQUIRED` إن نُسي الشكل) |
| السلة (`cart.html`) | `POST /carts`، و`GET /carts/:id`، و`PUT`/`DELETE /carts/:id/items/:productId?variantId=`، وسطر `available: false`. الزبون الداخل يجد سلته المحفوظة على أي جهاز (`GET /carts/mine`، و204 إن لم توجد) |
| إتمام الطلب (`checkout.html`) | `GET /checkout/options` (طرق الشحن بمدنها، والدفع، وهل يقبل كوبونات)، و`POST /checkout/quote` مع المدينة والكوبون، و`POST /orders` مع `Idempotency-Key`، والانتقال إلى `payment.redirectUrl` |
| الدفع (`pay.html`) | `GET /orders/:id?phone=` و`paymentExpiresAt`، ومسارات البوابة التجريبية |
| حسابي (`account.html`) | التسجيل والدخول مع `guestCartId` (دمج سلة الضيف، و`cartId` في الرد)، و`PATCH /customers/me` (`phone: null` يمسحه)، و`GET /customers/me/sessions`، و`POST /customers/logout` و`/logout-all`، و`POST /customers/me/password`، و`POST /customers/password-reset` |
| كلمة مرور جديدة (`reset.html`) | `POST /customers/password-reset/confirm` (الرمز لمرة واحدة، ويُخرج كل الأجهزة) |
| طلباتي (`orders.html`) | `GET /orders` (طلبات الزبون فقط، مرقّمة)، و`GET /orders/:id/events` (السجل الزمني)، و`GET /orders/:id/delivery` (اسم المندوب وهاتفه) |
| التتبّع (`track.html`) | `GET /orders/:id?phone=` كضيف، والسجل الزمني والتوصيل بنفس الشرط |
| تطبيق المندوب (`courier.html`) | `POST /staff/login`، و`GET /deliveries?status=` (توصيلاته فقط)، و`POST /deliveries/:orderId/pickup` و`/deliver` (مع `cashCollected`) و`/fail` |
| لوحة الإدارة (`admin.html`) | `POST /staff/login` أو مفتاح المالك، وأرقام البداية من `X-Total-Count`؛ الطلبات (`?q=&status=&paymentStatus=`، وآلة الحالات، و`PATCH /orders/:id/payment`، والإسناد `POST /orders/:id/delivery`، والاسترجاع مع `Idempotency-Key`)؛ المنتجات والأشكال والمخزون مع `ETag`/`If-Match` (412 إن عدّل زميل قبلك) و`null` في PATCH؛ الأقسام؛ الكوبونات؛ الزبائن (`?q=`)؛ الموظفون (`/staff`، والإنشاء والتعديل للمالك فقط)؛ سجل التدقيق (`GET /audit-log`) |

كل الأخطاء تصل بالشكل الموحد `{ error: { code, message, details, requestId } }`، والموقع يترجم `code` إلى رسالة عربية (`web/js/ui.js`)، ويعرض `requestId` ليذكره الزبون لخدمة العملاء.

كل المسارات في `../docs/API.md`. ويمكن أيضاً إدارة المتجر عبر الـ API مباشرة (Postman أو curl) بمفتاح المالك، مثلاً لتأكيد طلب:

```bash
curl -X PATCH http://localhost:3000/orders/<رقم الطلب>/status \
  -H "X-Api-Key: <OWNER_API_KEY>" -H "Content-Type: application/json" \
  -d '{"status":"confirmed"}'
```

## الأمان في الموقع

- **منع حقن الكود:** كل نص يأتي من الـ API يُهرَّب قبل عرضه، فاسم منتج فيه كود لا يُنفَّذ.
- **سياسة أمان المحتوى (CSP):** المتصفح لا يشغّل إلا سكربتات الموقع نفسه، ولا يتصل إلا بـ API المتجر.
- **الوصول للملفات:** خادم الموقع لا يسمح بالوصول لأي ملف خارج مجلد `web` (مثل `.env`).
- **CORS:** الـ API يقبل الطلبات من عنوان الموقع فقط (`CORS_ORIGIN`).
- **الجلسات:** تسجيل الخروج يُلغي الجلسة في الخادم فعلاً. توكن الموظف في `localStorage`، ومفتاح المالك في `sessionStorage` فقط.

## الاختبار

- **ضمن الفحص الشامل:** `npm run verify` في المجلد الرئيسي يفحص المتجر أيضاً (الخطوة "Maa Store: API + website (shop, courier, admin)"): الصفحات، وسياسة الأمان، ومدن التوصيل، وCORS.
- **اختبار في متصفح حقيقي:** شغّل المتجر (`npm start`) بعد `npm run seed` (يحتاج حسابات الموظفين والكوبون)، ثم في نافذة أخرى:
  ```bash
  npm run test:browser
  ```
  - **أي متصفح:** يفتح Chrome أو Edge أو Chromium بلا واجهة. على macOS يجد Chrome (أو Chromium أو Edge) في `/Applications` تلقائياً، وعلى Windows يجد Edge أو Chrome، وعلى Linux يبحث عن `google-chrome` و`chromium` و`microsoft-edge`. لمتصفح في مكان آخر: `BROWSER_PATH=<المسار> npm run test:browser`.
  - **رحلة الزبون:** تصفح، وتصفية بالقسم، وبحث، وسلة، وصفحة منتج بأشكاله، وإتمام طلب كضيف (المدينة والاستلام من المحل)، وتتبّع، وتسجيل، والشراء كزبون مع الكوبون `WELCOME10`، و"طلباتي".
  - **لوحة الإدارة:** دخول المدير (`admin@maa.ly`)، ولوحة البداية، وفتح طلب الزبون وإسناده لمندوب.
  - **تطبيق المندوب:** دخول المندوب (`courier1@maa.ly`) على شاشة هاتف، ثم الاستلام والتسليم مع تحصيل النقود. ثم يتأكد أن الزبون يرى "تم التوصيل" والسجل الزمني كاملاً.
  - **ماذا يفحص:** أي خطأ JavaScript أو مخالفة لسياسة الأمان، وأي تمرير أفقي (خلل في التصميم)، والرئيسية على شاشة هاتف.
  - **فحص الحقن (XSS):** ينشئ منتجاً مؤقتاً اسمه يحتوي كود HTML (بمفتاح `OWNER_API_KEY` من `.env`)، ويتأكد أنه يظهر كنص عادي ولا يُنفَّذ، ثم يحذفه.
  - **منافذ أخرى:** إن كان المتجر على منافذ غير الافتراضية: `SITE=http://localhost:5273 API=http://localhost:3100 npm run test:browser`.
  - **الصور:** يلتقط صورة لكل صفحة (ومنها لوحة الإدارة وتطبيق المندوب) في `tests/screenshots/`.
